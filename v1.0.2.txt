# 三、v1.0.2 的核心目标

本版本不要把“文件夹”理解成单纯的“景观分析文件夹”。

本版本要建立一个通用的：

# 「文件夹 / 数据空间」系统

它负责组织 Plan Identify 中的植物数据、观察数据、导入数据以及景观项目数据。

文件夹本身是一个通用容器。

其中可以存在三种主要类型：

### 1. 景观文件夹

用于：

* 校园
* 公园
* 小区
* 景区
* 景观项目
* 植物配置调查
* 景观植物分析

拥有额外的景观功能：

* 景观照片
* 地点
* 植物配置
* 植物层次分析
* 植物多样性分析
* 季相分析
* 色彩分析
* AI 景观分析
* 景观报告

---

### 2. 协作 / 导入文件夹

用于承载：

* 别人发送过来的植物数据
* 其他用户导出的植物库
* 外部数据集
* 多人调查数据
* 导入的 Excel / JSON / ZIP 等数据

它首先应该作为一个**数据接收区 / 数据暂存区**。

例如：

```text
👥 张三的植物数据
├── 凤凰木
├── 紫薇
├── 悬铃木
└── 鸡蛋花
```

用户确认数据以后，可以：

* 合并到自己的植物库
* 移动植物到其他文件夹
* 复制/加入植物到其他文件夹
* 执行重复检测
* 处理数据冲突
* 保留原始导入数据

---

### 3. 自定义文件夹

完全由用户自由创建。

例如：

```text
📁 我的常见植物
📁 广东植物
📁 待确认植物
📁 比赛项目
📁 课程作业
📁 2026植物调查
```

不需要具有特殊业务逻辑。

# 四、非常重要：PlantRecord 与 Folder 必须解耦

不要让一个 PlantRecord 只能属于一个文件夹。

一个植物记录可以同时存在于多个文件夹。

例如：

```text
悬铃木
 ├── 校园植物调查
 ├── 广东常见植物
 └── 我的植物库
```

不要复制出三个悬铃木 PlantRecord。

应该建立类似：

```text
PlantRecord
     │
     │ N:M
     ▼
FolderPlant
     │
     ▼
Folder
```

其中：

```text
PlantRecord
```

仍然是植物的核心数据资产。

而：

```text
Folder
```

只是组织和归类这些数据的容器。

这样可以实现：

* 添加植物到文件夹
* 从文件夹移除植物
* 移动植物
* 将植物加入多个文件夹
* 批量移动
* 批量加入
* 批量移除

删除文件夹时默认不能删除 PlantRecord。

删除文件夹只删除：

```text
FolderPlant
```

关系。

---

# 五、推荐的数据模型

根据当前项目架构自行调整，不要机械照搬。

建议建立：

```text
Folder
```

字段至少包括：

```text
id
name
type
description
coverImage
createdAt
updatedAt
```

FolderType：

```text
LANDSCAPE
COLLABORATION
CUSTOM
```

建立：

```text
FolderPlant
```

表示：

```text
Folder ↔ PlantRecord
```

建议包含：

```text
folderId
plantId
addedAt
sortOrder
```

必要时增加：

```text
source
note
```

# 六、景观文件夹扩展能力

不要额外创建一套完全独立的 PlantRecord。

景观文件夹直接引用现有 PlantRecord。

可以增加：

```text
LandscapeFolderData
```

或者采用合理的扩展字段 / 独立 Entity。

包含：

* location
* landscapeDescription
* projectType
* analysisResult
* analysisUpdatedAt

另外建立景观照片：

```text
FolderImage
```

或者根据现有图片架构设计合理的数据模型。

必须明确区分：

### 植物识别图片

属于：

```text
ObservationImage
```

例如：

* 叶片
* 花
* 果实
* 树皮
* 整株植物

### 景观照片

属于：

```text
Folder / Landscape
```

例如：

* 整个公园
* 花坛
* 道路绿化
* 植物群落
* 景观节点

两者不能混为一谈。

* JSON
* Excel

# 十、数据合并规则

导入数据后不能直接无脑插入。

必须经过：

```text
导入
 ↓
格式标准化
 ↓
字段校验
 ↓
本地重复检测
 ↓
疑似重复检测
 ↓
冲突检测
 ↓
用户预览
 ↓
用户确认
 ↓
正式合并
```

复用当前已经存在的数据清洗和去重能力。

不要因为本版本加入文件夹系统就重新实现一套去重算法。

# 十一、重复植物判断

禁止只通过中文名判断重复。

应该综合：

1. Latin name
2. 中文名
3. 科
4. 属
5. AI识别结果
6. 图片相似性（如果现有系统支持）
7. 观察记录
8. 其他已有字段

对于：

```text
确定相同
```

可以提供：

> 合并

对于：

```text
疑似相同
```

> 等待用户确认

不要未经用户确认直接破坏性合并。

* 花期
* 果期
* 叶色
* 植物用途
* 景观照片

```text

乔灌草层次
季相
色彩
植物配置
```

建议保存：


# 二十、最终验收标准

完成 v1.0.2 后，用户应该能够完成完整流程：

```text
创建文件夹
      ↓
选择文件夹类型
      ↓
添加已有植物
      ↓
拍摄 / 识别新植物
      ↓
植物进入 PlantRecord
      ↓
植物加入多个文件夹
      ↓
别人发送植物数据
      ↓
导入到协作文件夹
      ↓
自动检测重复 / 冲突
      ↓
用户确认合并
      ↓
保留所有有效观察记录
      ↓
将植物整理到不同文件夹
      ↓
如果是景观文件夹
      ↓
添加景观照片
      ↓
进行植物配置分析
      ↓
AI 景观分析
      ↓
生成 PDF / Excel 报告
```

最终的数据关系应该保持清晰：

```text
PlantRecord
    │
    ├── PlantObservation
    │       └── ObservationImage
    │
    └── N:M
          │
       Folder
          │
          ├── CUSTOM
          ├── COLLABORATION
          └── LANDSCAPE
                    │
                    ├── Landscape Images
                    ├── Plant Configuration
                    └── AI Analysis
```

最重要的原则：

> **PlantRecord 是植物本身，Folder 是组织植物的容器，Observation 是一次观察，Landscape 是文件夹的一种专业能力，而不是另一套植物数据库。**

开发过程中，如果发现现有项目的数据模型与上述设计存在冲突，不要强行照搬。优先保持现有项目的数据完整性，在现有架构基础上进行最小、可维护的扩展。

每完成一个大阶段：

1. 编译项目；
2. 运行测试；
3. 检查数据库 Migration；
4. 检查旧功能；
5. 检查新功能；
6. 修复发现的问题；
7. 再进入下一阶段。

不要为了追求一次性完成所有功能而留下大量 TODO、假实现或临时 Mock。
